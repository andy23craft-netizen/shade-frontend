# FEAT-99 -- Tenant Migration and Restore Drill

**Status:** Blocked on backend/operator tooling; no ordinary frontend feature work planned.

**Dependency group:** D -- release safety gate (may proceed alongside `FEAT-08`).

**Depends on:** Final V2 schema migrations, tenant-scoped setup/settings from `FEAT-06`, quote
storage from `FEAT-12`, and the backend's retained-data migration tooling.

**Primary owner:** Backend and operations.

## Objective

Provide a repeatable, tenant-explicit, data-preserving upgrade and disaster-recovery process,
then prove through drills that it cannot overwrite the wrong library or strand intact private
media assets.

## Required workflow

- Every schema change has both a clean-install representation and an ordered upgrade from the
  supported retained-data baseline.
- Restore input identifies an explicit source artifact and explicit target tenant; neither is
  inferred from hostname, recent activity, current working directory, or database contents.
- Validate artifact format, schema/version compatibility, source identity, target identity,
  required disk space, and asset expectations before mutation.
- Create and verify a pre-restore safety copy.
- Replay in temporary isolated space, run integrity and tenant-boundary checks, and activate
  atomically only after all validation passes.
- On injected or real failure, leave the active library unchanged or roll back completely and
  retain actionable operator diagnostics without exposing private content.
- Reconnect intact tenant-owned book-cover and album-artwork directories by catalog UUID.
  State plainly that database restore cannot recover asset files lost from disk.

## Acceptance criteria

- [ ] Clean install and retained-data upgrade reach the same current schema and required
      setup/settings/quote defaults.
- [ ] A rehearsed restore succeeds for each supported tenant without changing any other
      tenant's rows, settings, setup state, quotes, loans, memberships, or asset bindings.
- [ ] Wrong-source/wrong-target, malformed artifact, incompatible version, insufficient space,
      missing asset, interrupted replay, integrity failure, and activation failure scenarios
      are injected and documented.
- [ ] Every pre-activation failure proves the active target remains unchanged; every
      post-activation failure proves atomic rollback from the safety copy.
- [ ] UUID-based cover/artwork reconnection is verified for present files, while missing files
      produce honest non-destructive behavior.
- [ ] Operator logs redact credentials and private catalog/quote content while retaining a
      traceable run identifier generated by the tooling.
- [ ] A second operator can execute the runbook in a staging rehearsal using only documented
      prerequisites and can verify tenant identity before approval.
- [ ] Frontend smoke tests after restore cover setup gating, settings, Home quotes, both media
      catalogs, loans, covers/artwork, and unknown-host isolation.
- [ ] No browser backup download, restore inventory, filesystem path, threshold, or activation
      control is added.

## Operator questions requiring an explicit decision

1. What artifact identifier and signed/verified metadata prove the source tenant without
   trusting a filename?
2. Which operator must approve a cross-tenant restore, and is that operation allowed at all
   outside a documented disaster scenario?
3. What supported backup-version window and migration chain are guaranteed for V2?
4. What maintenance/read-only behavior prevents writes during atomic activation, and how is
   it surfaced to users?
5. How long are the pre-restore safety copy, failed temporary replay, and audit records
   retained, and who may remove them?
6. Which asset-mismatch conditions block activation versus complete with a warning?

## Out of scope

An ordinary frontend restore page, browser-visible backup inventory, browser-supplied paths,
automatic tenant inference, and recovery of media files that no longer exist on storage.
